# Reflection

One of the more interesting things I noticed building this was how much of the "loop engineering" principles mirror alot of the good practices and really low-level habits we learn in the foundations of undergrad and beginner-level concepts regarding engineering/computing discipline rather than introducing something new. The "propose, don't decide" pattern I designed for the weekly AI reviewer where the suggestions remain pending until the user explicitly accepts or rejects them is the same idea as a code review or CI/CD merge gate. The idea is that automation can assess and flag, but a human continues to be the final checkpoint before anything concrete actually changes. I see this pattern again and again, this time the idea manifested in a personal habit-tracking app project which made it clearer to me that the pattern is about not fully deferring to any automated process. I also learned the same lesson from the opposite direction in that hardcoding a specific spec in my plan prompt early on, and it broke without being noticeable the moment I added a second spec file for the extension step. The loop didn't cause that bug but it just executed any ambiguity I had in the loop quitely, which showed me that a loop just amplifies whatever quality already exist in your specs. It cannot correct for everything.
